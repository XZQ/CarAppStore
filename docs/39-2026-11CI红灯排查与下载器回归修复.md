## 2. 上一轮的错误结论

上一轮（docs/38）把 27 条 `RealFileDownloaderTest` 失败判定为「本机 Windows 裸 socket 测试服务器的预置问题」，依据是：

**这个判断错在什么地方**：复现成功只说明「不是 JDK 版本差异」，并不能推出「是环境问题」。真正的证据应该是**对照实验**——把代码回退到父提交看是否转绿。上一轮没有做这一步，也没有核查 CI 的实际状态，于是把一个真实回归当成环境噪声放过了。

第 7、8 步是决定性的：它们把「提前读状态码」和「HEAD 路径」两个变量单独隔离了出来。

## 4. 根因

JDK `HttpURLConnection` 的两个行为叠加造成了一条僵尸连接：

1. `openConnection()` 为了做手动重定向跟随，会先读 `connection.responseCode`。JDK 的 `getResponseCode()` 内部走 `getInputStream()`，这一步会**固定响应 body 流**并把 `cachedResponse` 置为 `true`。
2. `probeRemoteMeta()` 在拿到连接后**又调用了一次 `headConnection.connect()`**。此时 JDK 认为响应已经缓存，于是一条新的 TCP 连接被建立，却**跳过了发送请求头**（`writeRequests()` 在 `cachedResponse` 为真时不发数据）——这条连接上永远不会有请求。

于是：

- 服务端（单线程同步 `accept`）在这条僵尸连接上阻塞在 `readLine()`，**占住了唯一的 accept 槽位**；
- 后续所有分片 GET 连接排在 accept 队列里得不到处理；
- 客户端等不到响应，15 秒 `readTimeout` 后抛 `SocketTimeoutException`，被归类成 `NETWORK_TIMEOUT`。

生产环境的真实影响与测试一致：HEAD 探测（每次下载开始时都会做）污染连接池后，同一进程内后续的分片 GET 请求全部超时。服务端是否单线程只影响「堵死」的程度，不改变「GET 请求发不出去」这个事实。

## 5. 修复

| # | 位置 | 修复 |
| --- | --- | --- |
| 1 | `RealFileDownloader.probeRemoteMeta` | 删除多余的 `headConnection.connect()`。`openConnection` 已完成建连与响应头读取，再调 `connect()` 只会造出只握手不发送的连接 |
| 2 | `RealFileDownloader.openConnection` | 等待响应头期间注册中断钩子（`control.registerInterrupt { connection.disconnect() }`），让「收到取消/暂停」能立刻打断阻塞读，而不是干等满 `readTimeout` |
| 3 | `RealFileDownloader.openConnection` KDoc | 明确写出「返回的连接已完成建连并读完响应头，调用方不得再次调用 `connect()`」，并说明等待响应头期间可被停止指令打断 |

第 2 项修的是另一个真实缺陷：`a4c3d75` 只在**发起请求前**检查停止状态，等待响应期间没有中断钩子，取消信号会迟迟不生效（实测 `download 在进入分片下载前收到取消后会快速停止` 用例超时失败）。

## 8. 流程教训

1. **push 之后必须核查 CI 状态**。公开 API（`/actions/runs`）无需权限即可读到结论与失败步骤，本轮就是靠它才发现红灯；上一轮把「以 CI 为准」写进文档却没有真的去看。
2. **「本地能复现」不等于「环境问题」**。判定环境问题至少要有一组对照实验（回退到父提交 / 换环境 / 换 JDK 版本），而不是「换了 JDK 还是这样」。
3. **断言失败与超时是两回事**。`AssertionError: expected X but was NETWORK_TIMEOUT` 说明超时是**结果**不是原因；顺着失败码往上找，才能看到真正的阻塞点。
4. **探针优于推理**。在客户端与测试服务器两端各打一行日志（谁建立连接、谁读到请求行），10 分钟就能定位；纯读代码推理在 JDK 内部行为上花了更久且没收敛。
5. **回归测试要做反向验证**。新加的用例必须证明「放回 bug 会红」，否则它只是一条永远通过的装饰。
6. **不要把错误结论写进文档**。上一轮写下的「本机环境限制」免责声明，会让后续接手者据此跳过排查，本轮已全部更正。
