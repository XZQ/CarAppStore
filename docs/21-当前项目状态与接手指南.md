## 5. 关键架构决策

- **Repository**: `RealAppRepository` 代理到 3 个 DataSource，`FakeAppRepository` 仅用于测试
- **状态管理**: `DefaultStateCenter` + `StateReducer` 归约，自动推导 primaryAction 和 statusText
- **下载控制**: `DownloadExecutionControl` 支持 pause/cancel + `registerInterrupt` 连接级中断
- **数据持久化**: `VersionedJsonStore` 统一管理 JSON 文件的 schema 版本、迁移、并发锁、原子写
- **策略拦截**: `DefaultPolicyCenter` 检查 Wi‑Fi/存储，升级同时校验下载+安装策略；驻车规则只在 `vehicleInstallPolicyEnabled` 开启时参与
- **平台分流**: `supportedPlatforms/currentPlatform` 决定当前客户端是否可处理安装包，`UNSUPPORTED` 动作和业务管理器双重拒绝其他平台产物

- 远端数据已具备 HTTP/条件请求缓存/资源回退链路，但仍未接入真实 API
- `DefaultPolicyCenter` 已支持网络/存储实时信号并完成车载策略开关解耦；真实车载发行仍需接入具体 OEM 车况真值
- 安装链路需要在手机、平板和大屏设备上覆盖 Android 版本/ROM 差异；OEM/车载 ROM 只作为可选专项
- GitHub Actions hosted runner 已成功完成单测、编译、Lint、Debug/Release 构建和产物上传
- 仓库仍缺设备级自动化安装测试；当前通过的是本地 JVM/Robolectric/Lint/构建验证

### 性能优化剩余清单（2026-08-24 复盘，均未实施）

2026-08 性能专项已完成 22 项并全部提交（热路径节流、查询批量化、UI 差量刷新、调度器卸载、单调钟修复、分片缓存释放、打点轮转）。以下为**有意搁置**的候选项，按解锁条件分组；其中的收益数字在真机 profiling 之前均为推算值。

**第一组 · 需真机视觉回归才能动（UI 行为风险）：**

| 项 | 说明 |
| --- | --- |
| Home/Search 列表 RecyclerView 化 | `HomeAdapter` 已实现未接线（约 600 行、三套布局），需逐布局视觉回归 |
| DetailFragment 图片按变化刷新 | 静态绑定已拆分，图片重绑非热点，预期收益小 |
| 导航 back stack 复用 | 收益小，优先级最低 |

**第二组 · 需真机测量证明值得（架构级改动）：**

| 项 | 说明 |
| --- | --- |
| StateCenter 分 app StateFlow | 现为 `observeAll` 全量扇出，任一应用更新会推给全部订阅者；按 app 拆流可再降每 tick 成本，但七模块接口全动 |
| legacy 双写收敛 | repository 每次写盘同时维护新旧两种格式；何时放弃旧格式读者是版本/迁移决策，不是技术判断 |
| JSON 全文件重写的规模天花板 | 分片记录**已**按任务独立落盘（core `DownloadStore` 的 `temp/<taskId>/meta.json`），下载热路径不碰全局文件；剩余耦合是 `saveDownloadTask`（下载期间 ≤5 次/秒）重写含全部任务记录的 `structured_local_store.json`，任务记录为小对象，天花板比早期评估远得多。Room 或追加日志仍取决于产品规模需求 |
| `org.json` → `kotlinx.serialization` | 解析快约 2-5 倍、GC 更少；全模型与 store 层改造，需测量证明值得 |
| `VersionedJsonStore.read()` 深拷贝 | 每次读取做 `toString()`+重解析（`VersionedJsonStore.kt:46`）；热路径频率已被节流压低，优化需改快照语义 |
| repository 层内存缓存 | 可消掉剩余全量 JSON 读；前提是明确单进程边界——存储锁是进程级的，跨进程写会使缓存变脏 |
| OkHttp 替代 `HttpURLConnection` | 连接池/自动重试/HTTP2；当前网络调用非热点 |
| Baseline Profile | 冷启动已被 `AppContainer` 约 30 处 `by lazy` 压住，预期收益小 |

**第三组 · 已评估并明确暂不做（权衡后放弃）：**

| 项 | 放弃原因 |
| --- | --- |
| 下载协程硬中断 | 停止目前是协作式检查点；硬取消只快几百毫秒，但可能留下半写状态，与断点续传的崩溃一致性目标冲突 |
| `FileEventTracker` 关闭时排空写入队列 | 容器重建/进程退出会丢最后不足 1 秒的打点；加排空需在 shutdown 引入阻塞，对分析日志不值 |
| `AppContainer.shutdown()` 事件排空 | 同上 |

**元缺口 · 解锁第二组的前置动作：** 全部已实施优化基于代码静态推演，尚无 Perfetto/systrace 真机实测。下一步有信息量的动作是在真机上开一个下载任务抓 trace，确认热路径分布与推演一致，再决定第二组各项是否启动。
