为什么停在 21 而不是更高：

- AGP 8.13.2 要求 JDK 17 以上，21 是当前 LTS，Android 官方工具链推荐值。
- Gradle 8.14.x 的 JVM 支持上限是 Java 24，本机 Android Studio 自带 JBR 已到 25，直接用会以「Unsupported class file major version」失败。自检脚本对「高于基线但仍在 Gradle 支持范围内」的 JDK 只告警不拦截，对 25+ 明确拒绝并给出提示。

### 2.1 目录缓存的身份维度（#1）

```kotlin
private suspend fun loadVisibleCatalog(): List<RemoteCatalogItem> = catalogCacheLock.withLock {
    val nowNanos = monotonicClockNanos()
    val fingerprint = catalogSource.currentRequestFingerprint()
    cachedVisibleCatalog
        ?.takeIf { it.fingerprint == fingerprint && it.isFresh(nowNanos) }
        ?.let { return@withLock it.items }
    // ...重新加载并按 origin 记录 TTL
}
```

降级 TTL 取 3s 的取舍：足以让同一屏的 N 次并发查询共用一次失败结果，又不会把「刚才断网」的状态固定 30s；网络恢复后下一次调用就会重新请求远端。单调时钟回退（`elapsed < 0`）视为过期，避免设备休眠唤醒后时间跳变导致缓存长期命中。

### 2.2 信任策略的作用域（#2）

严格校验只针对 `AppPlatform.ANDROID in supportedPlatforms` 的条目。其他平台产物在下载/安装入口本来就会被拒绝，若一并按 Android 规则校验，会把「目录里同时下发 iOS 条目」这种正常配置误判为目录不可信，进而触发整份目录回退。宽松策略的入口收敛到两处：内置 raw 兜底 loader（内容由仓库自己保证）与 `BuildConfig.DEBUG && environment == LOCAL_SIM`；`AppContainer` 里 `catalogTrustPolicy` 与 `apkVerificationPolicy` 共用一个 `allowMissingTrustMetadata` 判断，避免两处口径漂移。

### 2.3 失败分类与主动作（#4）

| 失败码 | 分类 | 主动作 |
| --- | --- | --- |
| `POLICY_BLOCKED` | 环境类 | `RETRY_INSTALL`（条件解除后可成功） |
| `APK_MISSING` / `APK_INVALID` / `APK_PACKAGE_MISMATCH` / `APK_VERSION_*` / `APK_SIGNER_*` | 产物终态 | `RETRY_DOWNLOAD` |
| `INSTALLED_PACKAGE_*` / `INSTALLED_VERSION_*` / `INSTALLED_SIGNER_*` | 安装后事实不一致 | `RETRY_DOWNLOAD` |
| `PLATFORM_UNSUPPORTED` | 平台终态 | `UNSUPPORTED` |
| `SESSION_NOT_SUPPORTED` | 系统能力缺失 | `DISABLED` |

## 5. 本机环境限制（⚠ 本节结论已被推翻）

> **更正（2026-11-08 晚）**：本节原先判定「27 条 `RealFileDownloaderTest` 失败是本机 Windows 裸 socket 测试环境的预置问题」，该结论**错误**。真实情况是 `a4c3d75` 引入的下载器回归，在 CI（Ubuntu）上同样失败；本轮已定位根因并修复，详见 [docs/39-2026-11CI红灯排查与下载器回归修复](39-2026-11CI红灯排查与下载器回归修复.md)。下文保留原文以记录这次误判，避免同样的错误结论再次被引用。

本机 Windows 上 `:core:testDebugUnitTest` 全量执行时，`RealFileDownloaderTest` 有 **27 条失败**，表现为 `NETWORK_TIMEOUT` / `Read timed out`。

当时的排查结论（已证伪）：

- 测试内嵌的 HTTP 测试服务器收到了 `HEAD` 请求，但后续 `GET` 连接挂起，客户端阻塞在 `getResponseCode`。
- 已排除代理：清空 `http.proxyHost` / `https.proxyHost`、设置 `nonProxyHosts`、独立 Java 探针、`ProxyEnvProbeTest` 均未能复现正常路径。
- 用 JDK 17 加临时改回 17 的构建脚本复跑，**同样 27 条失败**，与本轮 JDK 21 迁移无关，于是被误判为「这台机器上裸 socket 测试设施的预置问题」。
- 排查用的探针测试与临时改动已全部清理，仓库没有残留。

**误判的原因**：复现成功只排除了「JDK 版本差异」，并不能推出「环境问题」；缺少「把代码回退到父提交」的对照实验，也没有核查 CI 的实际状态。真实根因是 JDK `HttpURLConnection` 在响应已缓存后再次 `connect()` 会建立一条「只握手、不发送请求头」的连接，占住单线程服务端的 accept 槽位，使后续分片 GET 全部超时。

## 6. 明确不改的边界

- 鉴权过期仍归类 `NETWORK_INTERRUPTED`，独立 `AUTH_EXPIRED` 失败码与重认证 UX 一起规划，不在本轮。
- 目录信任策略沿用 `AppCatalogValidator` 既有的**整份拒绝**语义：任一 Android 条目缺 `versionCode` 或签名摘要，整份来源被判不可信并回退到磁盘缓存 / raw 兜底。好处是失败关闭、不让缺元数据的条目进入 UI；代价是后端漏填一个字段会让整份目录降级。若将来需要「部分条目仍可用」，应引入条目级过滤，而不是放宽校验。
- 内存目录缓存仍是进程级、单槽位：多环境并存需要重启换容器，与 `AppContainer` 的重建语义一致，不额外做多槽 LRU。
- `EventReporter` 的待重试队列是内存队列，进程退出即丢失；跨进程持久化重试属于埋点上传服务的设计范围。
- 埋点上传服务、设备矩阵、正式签名、真实目录 / CDN 仍属外部条件，与 docs/36 结论一致。
