# 2026-11 第四轮深度审查与修复

> 本轮范围：对全部 13 个模块做新一轮深度审查（4 个并行只读审查 agent 覆盖并发/生命周期、资源/IO/安全、UI/壳层、工具链/CI，外加对下载/安装/升级/状态/策略/持久化/目录主链路的人工精读），修复确认的 4 个 P1 与一批 P2。

> 验证口径：以本轮提交 SHA 的 `carappstore-verification-<SHA>` CI 产物为准；本文不硬编码测试数量。

## 1. 修复清单（P1）

| # | 问题 | 位置 | 修复 |
| --- | --- | --- | --- |
| P1-a | **产物级失败后「重新下载」零网络死循环**：CHECKSUM_MISMATCH / MERGE_FAILED / 安装侧判定 APK 不可信（APK_INVALID 等）后，引擎已完成分片仍在盘上，续传逻辑判定「分片已完整」直接跳过网络请求，原样合并出同一份坏产物，反复失败 | `DefaultDownloadManager.prepareDownloadRecord` | 重试前若上次失败码属于产物级（下载侧 CHECKSUM_MISMATCH/MERGE_FAILED/REMOTE_FILE_CHANGED + 安装侧 `InstallFailureRetry.requiresFreshArtifact`），先 `clearCoreCache(taskId)` 再下载。与 StateReducer 的 RETRY_DOWNLOAD 判定共用同一分类；网络类失败不清缓存，续传行为不变 |
| P1-b | **生产环境缺省 sourcePolicy 走模拟下载产出假 APK**：目录条目漏写 `sourcePolicy` 时 DTO 硬编码 FALLBACK_SIMULATED，旁路环境 `allowMockSource=false`，模拟下载写假字节并报「完成」，到安装才以 APK_INVALID 失败 | `DownloadSourceResolver` / `AppCatalogDto` / `RealFileDownloader` / `AppDetail` / `DownloadRequest` | ① 解析器所有通向模拟的路径都受 `allowMockSource` 约束，禁止模拟时返回新增的 `REJECTED` 决策，下载器据此发 Failed；② DTO 未声明策略时保持 null，`AppDetail.sourcePolicy`/`DownloadRequest.sourcePolicy` 改为可空，由环境默认策略（PROD=DIRECT_HTTP）决定 |
| P1-c | **服务 stop/start 竞态致新下载「服务不可用」**：`stopIfIdle` 在销毁回调执行前清空 token，新 `startForegroundService` 被 AMS 投递给仍存活旧实例的 onStartCommand（不走 onCreate），旧实例不补握手，新 acquire 空等 10s 超时失败 | `AndroidDownloadExecutionHost` / `DownloadForegroundService` | 新增 `onServiceStartCommand`：已前台的旧实例收到新 start 时补完成等待中的 acquire，不重置 recovering（避免服务永远无法空闲停止）；onStartCommand 非 PAUSE 分支调用它 |
| P1-d | **4 页 lazy Adapter 未解绑滞留旧视图树**：MyApp/DownloadManager/InstallCenter/Upgrade 的 adapter 用 `by lazy` 跨视图重建存活，onDestroyView 未 `adapter=null`，返回栈期间整棵旧 item 视图树无法回收 | 上述 4 个 Fragment | onDestroyView 在 binding 失效前对 RecyclerView 置 `adapter=null`，与 Home/Search 既有做法对齐 |

P1-a、P1-c 均做了**反向验证**（临时移除修复后新增回归用例立即转红，恢复后转绿），符合 docs/39 §8 的回归测试纪律。

## 5. 明确不改 / 留作记录项

以下经评估**不在本轮改动**，避免引入超出验证能力的风险或破坏外部契约：

| 项 | 原因 |
| --- | --- |
| STRICT 强制 checksumValue | 属后端目录契约变更（docs/23/26），需后端联调确认，不能客户端单方面收紧 |
| OEM 驻车广播 API<33 隐式导出 | 可选车载平台问题；接收器必须导出才能收 OEM 广播，正确缓解是签名级 permission，需 OEM 协议约定 |
| ApkArtifactAccess 锁延伸到下载执行期 | 架构级改动，有死锁风险；当前由安装前身份校验 + 安装后事实核对兜底 |
| 策略设置更新串行化 / enteredSlot 锁外读 / 升级 install tryLock 空转 / 目录 HTTP 可取消 | 并发 P2，需更细的锁设计与真机验证，留作后续专项（见 §6） |
| MyApp 虚构资料/统计死 UI、CatalogPage 文案本地化 | 视觉/本地化改动，按 docs/21 需真机视觉回归，不在无设备证据时改动 |
| 303 重定向保持 HEAD | 协议瑕疵，服务端普遍兼容，收益极低 |

## 6. 剩余并发专项（建议下一轮）

1. 策略设置「读旧值-变换-落盘-发布」整体串行化（Mutex），消除快速切换开关丢失与内存/磁盘分叉。
2. `enteredSlot` 在 executionMutex 内一并返回快照；暂停终态写入只交给下载协程，避免命令协程用旧 progress 覆盖。
3. 升级编排的安装阶段在产物锁被占用时立即收敛为可重试失败，而不是空转轮询 30 分钟。
4. 目录 HTTP 用 `suspendCancellableCoroutine + invokeOnCancellation{disconnect}` 支持取消，缩小 catalogCacheLock 持有范围。
5. Debug 开发者设置页文件统计/清理移入 IO（仅 Debug 可达）。
